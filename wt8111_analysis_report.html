🗺️ map_obj.json 数据结构

返回格式：JSON 数组，每个元素是一个地图对象

{
  "type": "ground_model",       // 对象类型
  "color": "#174DFF",           // 阵营颜色十六进制
  "color[]": [23, 77, 255],     // RGB 数组
  "blink": 0,                   // 是否闪烁
  "icon": "MediumTank",         // 图标类型
  "icon_bg": "none",            // 背景
  "x": 0.586873,                // 归一化 X 坐标 (0~1)
  "y": 0.642267,                // 归一化 Y 坐标 (0~1)
  "dx": -0.978299,              // 方向向量 X（仅 Player 有）
  "dy": -0.207199               // 方向向量 Y（仅 Player 有）
}

参数值含义

❓ 关键问题：有没有高度数据？

结论：没有。 所有 ground_model 对象只有 x, y 两个坐标，没有任何高度字段（z / alt / altitude / height 均不存在）。

ground_model 的完整字段列表：

['blink', 'color', 'color[]', 'dx', 'dy', 'icon', 'icon_bg', 'type', 'x', 'y']

即使飞机出现（type 变为 air_model），根据 8111 端口的设计逻辑，大概率仍然只有 2D 坐标。这是因为 8111 的 map_obj 本质上是小地图数据，而小地图本身是俯视图，不包含高度维度。

❓ 关键问题：/state 在陆战能用吗？

结论：不能。 整个监控期间 /state 始终返回 {"valid": false}，即使在驾驶坦克移动中也是如此。

这与 PowerBroker2/WarThunder 文档一致——该库明确标注 "NOT tanks"。/state 端点只在空战中有效，提供己方载具的经纬度、航向、空速、俯仰/滚转等。陆战中无法获取己方精确位置。

📐 对空提前量计算可行性评估

最终结论：用 8111 端口在陆战街机做对空提前量计算 —— 不可行。
所需数据8111 可用性问题
敌机水平位置⚠️ 可能有需飞机出现在小地图上；坐标为归一化 2D
敌机高度❌ 无致命缺陷：无法计算 3D 距离和弹道下坠
敌机速度⚠️ 可估算用连续快照差分计算，但精度受采样率限制
敌机航向⚠️ 可能有若有 dx/dy 字段可获取方向，但未在非 Player 对象上验证
己方位置❌ 无/state 在陆战不可用；只能用 Player 对象的 x/y 代替
己方航向⚠️ 有 dx/dyPlayer 对象有方向向量，但精度未知
炮弹初速❌ 无需从 Datamine 拆包获取
距离⚠️ 可算水平距离可算，但 3D 斜距缺高度无法计算

三个致命问题

  1. 没有高度 → 无法算 3D 距离 → 无法算炮弹飞行时间 → 无法算弹道下坠 → 提前量公式缺失核心输入
  2. /state 不可用 → 己方位置只能从小地图归一化坐标估算，精度约 ±41m（0.01 归一化单位），对近距离对空射击而言误差太大
  3. 更新频率约 1-3 Hz → 飞机 500 km/h 时两次采样间移动 46-139m，速度估算误差极大

💡 还能用 8111 做什么？

虽然对空提前量不可行，但 8111 在陆战中仍有用途：

  • 小地图雷达 — 实时显示敌友位置，类似 WTRTI 的 HUD 功能
  • 敌方位置警报 — 检测红色单位接近，声音/视觉提醒
  • 占领区监控 — 实时显示 A/B/C 点状态和占领进度
  • 速度/仪表 HUD — /indicators 可用，显示速度、RPM、乘员状态等
  • 战斗录像分析 — 持续记录 map_obj 时序数据用于战后复盘
  • Discord 状态 — 显示在战斗中、驾驶什么载具

🔄 如果一定要做对空提前量？

唯一可行路线：截图 + 计算机视觉（不依赖 8111）

  • 用 OpenCV/YOLO 从游戏画面识别飞机轮廓和位置
  • 从像素位置 + 仰角估算 3D 位置（需要相机标定参数）
  • 用连续帧差分计算角速度
  • 结合炮弹初速（从 Datamine 获取）计算提前角
  • 在屏幕上叠加预测瞄准点

⚠️ 但这条路线复杂度高，需要训练模型、实时截图处理、屏幕标定，且可能违反游戏 ToS。
